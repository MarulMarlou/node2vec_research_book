# Сравнение Node2Vec и TransE: первый пилот на реальных данных (10.11.2026)

**Состояние:** промежуточная проверка работоспособности двух алгоритмов; **не итоговый научный результат** и **не выполнение 30+ сравнительных экспериментов**.

## Исходные данные и воспроизводимость

Источник — оригинальные CSV Book-Crossing. Хеши исходных файлов из переданного отчёта проверены и совпали с имеющимися файлами:

- `BX-Books.csv`: SHA-256 `b7a21c9332e39226758a3dce6365f1a5c23653514ca445b419b938adf5b41ce6`
- `BX-Book-Ratings.csv`: SHA-256 `f359084e5f350151b61f3d07acbe3c6ff0e2bd057d88901fa60507449d0e0e57`

Режим `quick`, split seed=2028, model seed=42. Число взаимодействий: train=4 594, validation=820, test=1 004; обучающий граф: 1 717 вершин, 6 594 связи. Четыре выполненных обучения: по два варианта Node2Vec и TransE. Жанровых рёбер в этом опыте нет.

| MRR@10 | 0,02402 | **0,04115** |
| P@20 | 0,00859 | **0,00898** |

P/R/F1/NDCG и MRR рассчитаны на 128 пользователях с положительными тестовыми оценками. AUC-ROC возможно посчитать только для 91 из них (71,09%), у которых в test были **обе категории** явно наблюдавшихся оценок: 7–10 и 1–6. Неизвестные взаимодействия не выдавались за заведомо отрицательные.

## Что показывает пилот

По NDCG@10, P@10, MRR@10 в этих конкретных условиях TransE превосходит Node2Vec; Node2Vec превосходит по R@10 и R@20. AUC обеих моделей близок к случайному ранжированию (0,5). **Одного split и одного model seed недостаточно** для вывода об устойчивом превосходстве какого-либо алгоритма. Нельзя сравнивать наблюдаемые времена обучения с другими компьютерами без описания конфигурации.

## Обнаруженное ограничение и исправление (после пилота)

В исходном `src/vkr_compare_embeddings.py` ограничение `max_users/max_books` выполнялось **до** окончательного переноса явно низких оценок в validation/test; затем каталог фильтровался повторно. Это создавало риск использования информации о будущем holdout при отборе элементов, хотя сами тестовые рёбра не попадали в train-граф.

**Исправлено:** сначала положительные и низкие оценки полностью распределяются по train/validation/test; затем пользовательский и книжный каталог отбирается **один раз, только по итоговому train**. Добавлен регрессионный тест инвариантности отбора относительно заранее сформированного holdout. Этот пилот проведён **до исправления** и сохраняется лишь как диагностический результат; для финальной серии требуется повторение на исправленном коде.

Дополнительно к двум моделям добавлен **train-only popularity baseline** — контроль качества относительно ранжирования по числу положительных оценок в train. В старом JSON этого baseline нет. После каждого обучения обновляется `comparison_experiments.csv`, после полного завершения формируется `comparison_config_summary.csv` с mean/std по независимым seed.

## Как продолжить

Обновить ветку и повторить `compare-quick`, убедиться в наличии `popularity_baseline` и новом отчёте. Затем выполнить `compare-full`:

```powershell
git pull --ff-only origin feature/vkr-stage1-typed-graph-holdout
powershell -ExecutionPolicy Bypass -File .\scripts\run_vkr_windows.ps1 -Mode compare-quick -SkipInstall
powershell -ExecutionPolicy Bypass -File .\scripts\run_vkr_windows.ps1 -Mode compare-full -SkipInstall
```

**Важно:** `compare-quick` и `compare-full` используют одну папку `results/comparison`; перед повторным запуском сохраните пилот при необходимости. При `compare-full` по умолчанию применяется **новый split seed=2030**, отличный от ранее просмотренного quick seed=2028. Полная сетка — **42 фактических запуска при её завершении** (24 Node2Vec, 18 TransE); в отсутствие `comparison_report.json` с `experiments=42` полная серия **не подтверждена**.

После выполнения необходимы таблицы и графики влияния параметров, анализ средних/стандартных отклонений, сравнение с popularity и научные выводы. Обязательны также дальнейшие работы с жанрами и полнотой первого этапа.
